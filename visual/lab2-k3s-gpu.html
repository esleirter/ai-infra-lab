Fase 1 · Lab 2

Kubernetes con GPU

Montar k3s en Linux nativo, exponer la GTX 1650 SUPER al scheduler, y entender qué de todo esto cambia al pasar a EKS.

1 · Instalación de k3s

Cluster real sobre el host, con containerd nativo. Sin capas intermedias.

CONFIG PRIMERO

El archivo de configuración se carga sin importar cómo se instale k3s, y el script de instalación no lo gestiona. Por eso conviene crearlo antes.

sudo mkdir -p /etc/rancher/k3s
sudo tee /etc/rancher/k3s/config.yaml <<'EOF'
write-kubeconfig-mode: "0644"
node-label:
  - "gpu=true"
  - "gpu.model=gtx1650super"
EOF

write-kubeconfig-mode evita tener que copiar el kubeconfig con sudo. Las node-label sirven después para nodeSelector — la misma mecánica que se usa con Karpenter en EKS.

INSTALAR 
curl -sfL https://get.k3s.io | sh -

echo 'export KUBECONFIG=/etc/rancher/k3s/k3s.yaml' >> ~/.bashrc
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml

kubectl get nodes --show-labels

Versión instalada en este lab: v1.36.2+k3s1 · containerd 2.3.2-k3s2

POR QUÉ NO EL BINARIO SUELTO

La doc de k3s ofrece instalar descargando el binario directo, pero advierte que no es útil para instalaciones permanentes: corre en primer plano y muere al cerrar la terminal. El script lo deja como servicio de systemd, sobrevive reinicios, y genera k3s-uninstall.sh para limpiar todo.

LO QUE k3s HIZO SOLO

Al arrancar, k3s escanea el host. Como el NVIDIA Container Toolkit ya estaba instalado del Lab 1, registró el runtime y creó el RuntimeClass automáticamente:

$ sudo grep -A6 nvidia /var/lib/rancher/k3s/agent/etc/containerd/config.toml

[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.'nvidia']
  runtime_type = "io.containerd.runc.v2"
[...runtimes.'nvidia'.options]
  BinaryName = "/usr/bin/nvidia-container-runtime"
  SystemdCgroup = true

Nótese el detalle: runtime_type es runc, pero el BinaryName apunta a NVIDIA. Al final es runc — solo cambia quién prepara el OCI spec antes.

2 · Los cuatro errores del camino

Cada uno enseña una pieza distinta de la cadena. Despliega para ver el diagnóstico.

Error 1 — Las labels no se aplicaron node-label ausente

La primera ejecución del script arrancó k3s antes de que existiera el config.yaml. Al volver a correrlo:

[INFO] No change detected so skipping service start

Causa: el script no reinicia el servicio si el binario no cambió. La config nueva nunca se leyó.

Solución:

sudo systemctl restart k3s
Error 2 — El device plugin no ve la GPU Incompatible strategy detected auto

El pod arranca 1/1 Running, pero en los logs:

E factory.go:112] Incompatible strategy detected auto
E factory.go:113] If this is a GPU node, did you configure
                  the NVIDIA Container Toolkit?
I main.go:381] No devices found. Waiting indefinitely.

El mensaje despista. El toolkit sí estaba configurado. El problema es que ese pod concreto corría con runc, así que no tenía /dev/nvidia* adentro. Y el plugin necesita ver la GPU para poder contarla y anunciarla.

Solución:

kubectl -n kube-system patch daemonset nvidia-device-plugin-daemonset \
  --type='json' \
  -p='[{"op":"add","path":"/spec/template/spec/runtimeClassName","value":"nvidia"}]'

Es el error más común montando GPU en Kubernetes a mano. El GPU Operator lo evita porque aplica el RuntimeClass a todos sus componentes.

Error 3 — RuntimeClass sin recurso, y recurso sin RuntimeClass No such file or directory

Dos pods, dos fallos distintos, misma lección:

PodRuntimeClassRecursoResultado
test-connvidia— Runtime activo, pero sin saber qué inyectar
test-gpuruncgpu: 1 Recurso reservado, pero runc no inyecta nada
gpu-testnvidiagpu: 1 Funciona

Cada pieza hace una mitad:

  • resources.limits: nvidia.com/gpu: 1 es la solicitud. El scheduler ubica el pod y el device plugin inyecta NVIDIA_VISIBLE_DEVICES. Pero eso solo escribe una variable de entorno.
  • runtimeClassName: nvidia es quién ejecuta. Es el único que sabe leer esa variable y actuar sobre ella.

Sin RuntimeClass: alguien escribió la orden, pero quien la ejecuta no sabe leerla.
Sin recurso: el que sabe leer está ahí, pero no hay orden que leer.

En Docker --gpus all hacía las dos cosas de golpe. Kubernetes separa responsabilidades: el scheduler asigna, el runtime materializa.

Error 4 — nvidia-smi no está en el PATH executable file not found in $PATH 
OCI runtime create failed: runc create failed:
exec: "nvidia-smi": executable file not found in $PATH

Causa: el binario se inyecta en un hook de prearranque, pero el command del pod se resuelve contra el PATH de la imagen antes de eso.

Solución: usar ruta absoluta /usr/bin/nvidia-smi, o directamente una imagen CUDA — que es lo que se haría en producción de todos modos.

3 · El manifiesto que funciona

apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  runtimeClassName: nvidia          # quién ejecuta
  restartPolicy: Never
  containers:
  - name: cuda
    image: nvidia/cuda:12.4.1-base-ubuntu22.04
    command: ["nvidia-smi"]
    resources:
      limits:
        nvidia.com/gpu: 1            # qué se pide

La cadena completa, paso a paso

1. Scheduler busca un nodo con nvidia.com/gpu disponible 2. Device plugin responde al kubelet con el UUID de la tarjeta 3. Kubelet inyecta NVIDIA_VISIBLE_DEVICES=GPU-<uuid> 4. nvidia-runtime lee la variable, modifica el OCI spec: · /dev/nvidia0, /dev/nvidiactl, /dev/nvidia-uvm · libcuda.so, libnvidia-ml.so · binario nvidia-smi · permisos cgroup de los devices 5. runc arranca el contenedor con el spec modificado
RESULTADO 
$ kubectl describe node b550-aorus | grep -A8 Capacity:
Capacity:
  cpu:                12
  memory:             16317660Ki
  nvidia.com/gpu:     1
  pods:               110

Kubernetes no descubre hardware por sí solo. El kubelet solo conoce CPU, memoria, almacenamiento efímero y hugepages — están cableados en el código. Todo lo demás necesita un device plugin que se lo anuncie vía gRPC.

4 · Eliminar el RuntimeClass de cada pod

Tener que declararlo en cada manifiesto es tedioso, y en producción nadie lo hace.

sudo cp /var/lib/rancher/k3s/agent/etc/containerd/config.toml \
        /var/lib/rancher/k3s/agent/etc/containerd/config.toml.tmpl

sudo sed -i 's/default_runtime_name = "runc"/default_runtime_name = "nvidia"/' \
        /var/lib/rancher/k3s/agent/etc/containerd/config.toml.tmpl

sudo systemctl restart k3s

Se edita el .tmpl, no el archivo normal. k3s regenera config.toml en cada arranque; un cambio directo se pierde al reiniciar.

Con esto, un pod que solo pide nvidia.com/gpu: 1 ya funciona. Es exactamente lo que hace el GPU Operator en EKS por debajo.

¿Y si un microservicio no necesita GPU? No pasa nada. El runtime nvidia lee NVIDIA_VISIBLE_DEVICES; si no está definida, no inyecta nada y delega en runc sin tocar el spec. El pod corre idéntico a como correría con runc — porque al final es runc.

En EKS el tema ni se plantea así: los nodos CPU y GPU son NodeGroups distintos, y los nodos GPU llevan un taint que repele todo lo que no lo tolere explícitamente. Eso es lo que evita que un pod cualquiera termine ocupando una p5 de $30/hora.

5 · Qué cambia en EKS

La pregunta práctica: en EKS no hay acceso al host. ¿Qué hay que hacer entonces?

AQUÍ · k3s
  • Instalar driver NVIDIA a mano
  • Pelear con DKMS y GCC
  • Instalar Container Toolkit
  • Configurar containerd
  • Instalar device plugin
  • Parchear el DaemonSet
  • Cambiar el runtime por defecto
ALLÁ · EKS
  • Elegir el AMI acelerado correcto
  • Instalar device plugin (según AMI)

Todo lo demás viene preinstalado y validado por AWS.

TRES DETALLES QUE IMPORTAN

1 · CUDA ya no viene en el AMI. Las librerías de espacio de usuario salieron de los AMIs acelerados de AL2023. Hay que incluirlas dentro del contenedor de la aplicación. Es la misma regla del Lab 1: driver en el host, CUDA en el contenedor.

2 · EFA necesita su propio device plugin. Aparte del de NVIDIA. Si vas a usar p4d/p5 con red de baja latencia, es un componente adicional.

3 · No uses Deep Learning AMIs. Están pensados para EC2 standalone y no traen kubelet ni la configuración de containerd que EKS necesita.

El taint que protege el presupuesto

# En el NodeGroup / NodePool de Karpenter
taints:
  - key: nvidia.com/gpu
    effect: NoSchedule

# En el pod que sí necesita GPU
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule

Sin ese taint, cualquier pod puede aterrizar en una instancia GPU. Con Karpenter, además, los nodos GPU solo se aprovisionan cuando hay pods pendientes que los toleran — y se apagan cuando no.

Por qué este lab importa

En EKS habrías escrito dos comandos y todo funcionaría. Aquí funcionó también — pero después de resolver cuatro errores, y eso deja claro qué componente resuelve cada uno.

Cuando el GPU Operator falle en producción — y va a fallar — la diferencia entre revisar el device plugin, el RuntimeClass, el taint o la versión del driver es saber para qué existe cada pieza.
